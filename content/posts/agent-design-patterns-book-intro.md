### 这本书在讲什么

《Agent设计模式：图解可复用智能体架构》（黄佳，人民邮电出版社）是 **Agent 时代的架构设计与工程实践指南**，旨在连接传统软件工程与大模型应用。

全书分为上下两篇：

- **上篇：智能设计的哲学**——以历史演进为线索，剖析软件范式从"确定性结构"向"概率性智能"的演进，揭示 Agent 诞生的必然性
- **下篇：六大类 21 个核心设计模式**——系统构建感知、记忆、推理、行动、反思、协作的通用架构，提供可复用的方法论

> **核心问题：如何在不确定的大模型上构建可靠的系统？**

<!--more-->

---

**📌 一句话总结：** 从 GoF 设计模式到 Agent 设计模式，是软件工程从"精密机械"向"自组织生命体"的范式跃迁。21 个可复用架构模式，让 AI 系统像搭积木一样可靠构建。

**🔥 核心观点：**
- **确定性已死**：软件不再是"瑞士手表"，而是"热带雨林"——拥抱不确定性，才能反脆弱
- **意图 > 模式**：GoF 模式告诉我们"怎么做"，Agent 时代"想做什么"才是关键
- **感知-记忆-推理-行动-反思-协作**：六大类模式构建完整智能体
- **MCP + A2A**：双轨协议让 Agent 连接工具、连接彼此，如同 USB-C 统一设备连接一样统一 AI 世界
- **园丁而非建筑师**：Agent 时代架构师的新角色——优化数据"土壤"、设置护栏"篱笆"、容忍适度失控

**💡 最打动人的比喻：** "机器何时拥有灵魂？当它开始为自己的错误感到不安时。"

---

2012年，Netflix 开源了一个"疯狂"的项目：Chaos Monkey——专门在生产环境中随机杀死自己的服务器。这在传统软件工程时代不可想象，但 Netflix 的逻辑很简单：既然故障不可避免，就让系统通过持续的小创伤进化出真正的免疫力。

同年，Google 发表论文"Datacenter as Computer"，宣告硬件故障不再是意外，而是统计学必然。软件设计的目标从"防止故障"转向"在故障常态化中依然可靠"。

这两个信号共同指向一个深刻的范式迁移：**确定性时代落幕，软件工程正在从精密的瑞士手表，变成自组织的生物群落。**

而这场变革最耀眼的主角，就是 Agent。

## 五条 Agent 设计原则

贯穿全书的元框架，是理解整本书的基础：

- **目标优先**：一切从"要达成什么目标"出发，而非先考虑"能调用什么工具"
- **上下文为王**：提示只是冰山一角，真正决定智能体行为的是上下文工程与记忆治理
- **显式反馈**：将反馈、反思与改进视为核心能力，内建于系统设计之初
- **渐进自治**：让系统在安全护栏内逐步提升自主决策能力
- **涌现优于规定**：设计让智能体自然涌现行为的机制，而非硬编码每一步


## 上篇：智能设计的哲学

### 第1章：从结构到智能——设计模式的世纪旅程

#### 1.1 模式思想的起源

"模式"概念并非 GoF 首创，灵感来源于建筑师克里斯托弗·亚历山大的《建筑模式语言》——优秀建筑是"永恒形式"的发现与组合。1994年 GoF 出版《设计模式》，提炼出23种模式，构建了系统化的设计世界观。

当手段被神圣化，"模式病"(Patternitis) 随之出现——过度设计让简单功能淹没在抽象海洋中。

**黄金时代的四次革命：**

| 革命 | 核心贡献 |
|------|---------|
| 工业化狂欢 | Java(1995)、C++(1998)、C#(2000) 使 OOP 成为工业标准 |
| 分层抽象 | MVC + DAO 让核心业务逻辑与存储技术解耦 |
| 依赖反转 | Spring 将依赖注入从理论推向实践 |
| 策略模式 | 算法成为可替换零件 |

然而，追求代码"纯洁性"也筑起了高墙——软件工程走向象牙塔，开发者沉醉于打造完美的水晶球，却忽视了应对现实世界复杂性的灵活性。

#### 1.2 诸神的黄昏：当确定性遇到不确定性

GoF 设计模式诞生于"静态世界"——系统边界清晰、需求变更可预测、运行环境稳定。然而 21 世纪，一切都变了。

**第一声警报：Twitter 2008 年宕机**

服务器仍在运行，每个组件看似正常，但整个系统陷入泥潭，响应时间从毫秒级退化至分钟级。开发者发现每个设计模式都待在它该在的位置——但"正确的设计"无法解决"规模"带来的问题。

**不确定性的三重奏：**

- **规模不确定性**：用户量从千人跃升至亿人，分布式成为常态
- **行为不确定性**：Web 2.0 时代用户行为不再可预测
- **需求不确定性**：花数月画 UML 按图施工的模式被打破

**经典模式的失效：**

| 模式 | 失效原因 | 业界应对 |
|------|---------|---------|
| 单例模式 | 分布式时代变瓶颈+单点故障源 | Netflix：放弃单例，拥抱冗余 |
| 工厂方法模式 | 无法处理运行时演化 | Tesla 自动驾驶每天学习新"驾驶模式" |
| 观察者模式 | 分布式环境下事件链雪崩 | 引入异步+背压机制 |

**转折点 2012-2014：四次关键变革**

- **Google "Datacenter as Computer"(2012)**：从"单机精修"到"宏观概率"——硬件故障是统计学必然，软件为"故障常态化"设计
- **Netflix Chaos Monkey(2012)**：从"鲁棒性"到"反脆弱"——系统像免疫系统，通过持续小创伤进化
- **Docker(2013)**：不可变基础设施——服务器从"需要维护的资产"变成可销毁的"耗材"
- **Kubernetes(2014)**：声明式 API + 调解循环——K8s 的 Controller 本质上就是原始的、针对特定任务的 Agent

> **确定性时代终结。软件不再是精密的瑞士手表，而更像自组织的生物群落。**

### 第2章：从模式到意图——软件工程的范式迁移

GoF 模式只告诉我们"怎么做"，Agent 时代**意图比模式更重要**——Agent 首次将"意图"显式嵌入系统。

#### 2.1 函数与流：计算的原子化

**无状态 → 纯函数**：LLM 本质是一个庞大且无状态的**纯函数**。FP 的"引用透明 + 管道"思想与 Agent 数据处理管道完全吻合：

`输入 Prompt → 检索增强 → 思维链推理 → 格式化输出`

软件工程跳出"对象身份"执念，回归"数据变换"本质。

**响应式流 → Agent 协作**：背压(Backpressure)机制让多 Agent 协作中"搜索 Agent"不会压垮"写作 Agent"。

> **智能的本质，是对变化的响应。** 神经网络响应 Tensor 流，强化学习响应 Reward 流，LLM 响应 Token 流。

#### 2.2 分布式的解耦：从单体到生态

- **微服务 API**：为 Agent 调用工具提供了网络基础设施
- **K8s 声明式 → Agent 意图编排**：K8s 的 Controller 是原始 Agent；**LLM Agent 是管理业务逻辑的"Kubernetes"**

| | Kubernetes | LLM Agent |
|--|-----------|-----------|
| 输入 | 语法严格的 YAML（静态资源需求） | 模糊多变的自然语言 Prompt（动态人类意图） |
| 职责 | 设计精确预设的流程图 | 设计目标函数 + 边界护栏 |

#### 2.2.3 Serverless：极致的原子能力

Serverless 将计算粒度从"服务"细化为"函数"。函数平时"沉睡"在云端，事件触发时才激活——从"维护一口永不干涸的井"到"按杯取水"。

在 Agent 架构中，Serverless 函数如同**"沉睡的技能"**——成千上万个工具部署为函数，Agent 在产生特定意图的瞬间通过 API 唤醒。

> 软件不再是以"大教堂"形态存在的固态结构，而是演变为流动不息的**"海洋"**——如同液体一般自由流动、动态组合与即时拆解。

#### 2.3 软件 2.0：当概率遇见代码

2017 年，安德烈·卡帕西(Andrej Karpathy)发表"Software 2.0"：**此前软件工程致力于消除不确定性；此后，软件工程开始学会利用不确定性。**

| | 软件 1.0 | 软件 2.0 |
|--|---------|----------|
| 开发者角色 | "建筑师"——精确控制每一行逻辑 | "园丁"——提供"土壤"（数据）和"栅栏"（损失函数） |
| 逻辑来源 | 人类编写 if-else | 模型从海量数据中自行"涌现" |
| 核心 | 确定性 | 概率性 |

**MLOps 的启示**：当代码演变为数据（模型权重），传统 DevOps 工具链力不从心。MLOps 为 AgentOps 铺平了道路。

#### 第2章小结：地基的夯实

| 技术演进 | 为 Agent 铺垫 |
|---------|--------------|
| 函数与流 | 使软件契合 AI 的思考节奏 |
| 分布式 + Serverless | 为 Agent 提供无限延展的"手脚" |
| 软件 2.0 | 在不确定性中建立对确定性的信心 |

所有关键技术的"积木"（Transformer、Docker、API、向量数据库等）如今都已准备就绪。我们需要的，是将它们整合，构建出具备**感知、记忆、思考与行动能力的"新物种"**。

### 第3章：从设计到演化——欢迎来到 Agent 时代

> 我们不再是在**设计**(design)一个系统，而是在**培育**(cultivate)一个物种。

把 LLM 引入软件架构的核心，软件不再仅仅是对人类指令的**响应(response)**，而是开始展现出**意图和自主性(agency)**。

#### 3.1 Agent 的本质：从工具到伙伴

**交互原语的升维**：从"命令与控制"转向"意图与协作"——Agent 更像一位经验丰富的同事，而非机械的命令行工具。

**意图的理解：模糊与精确的桥梁**

Agent 的核心能力是充当**"模糊翻译器"**，搭建"人类模糊的自然语言"与"机器精确的 API 调用"之间的桥梁，包含四层：语义理解 → 目的识别 → 上下文关联 → 风险评估与澄清。

**记忆与身份：Agent 的自我连续性**

工具是"用完即走"，Agent 有记忆——它在每次对话之间延续"身份"，逐渐形成对用户的深入理解。

**上下文工程：理解世界状态**

对 Agent 而言，**上下文就是它的整个世界**——"Garbage in, garbage out"。Agent 失败的原因，往往不是模型能力不足，而是上下文信息有误。

**任务分解：把"目标"变为"计划"**

任务分解(Task Decomposition)是衡量 Agent 智能化水平的关键指标。

**工具、技能与 ReAct**

2024 年兴起的 **MCP（Model Context Protocol）** 使 Agent 能像插拔 USB 设备一样灵活挂载外部能力。

> **MCP 的核心价值：把 AI 连接外部世界的方式标准化——就像 USB-C 统一了设备连接，MCP 正在统一 AI 与工具、数据的交互协议。**

Anthropic 2025 年发布的 **Agent Skills** 进一步区分：

- **工具(Tool)**：原子化操作，如"执行 SQL""发送 HTTP 请求"——是 Agent 的**"手"**
- **技能(Skill)**：能力单元 = 工具 + 领域知识 + SOP——是 Agent 的**"技能书"**

**ReAct 范式**（Thought → Action → Observation）已成为现代 Agent 行动的标准心智模型。

#### 3.2 Agent 心智架构：感知—推理—行动循环

传统软件架构本质是线性管道（输入→处理→输出），Agent 则运行在 `while(alive)` 的无限循环中：

| | 传统程序 | Agent |
|--|---------|-------|
| 逻辑 | 确定性的 if-else | 柔性的、与经验相关的推理 |
| 输出 | 执行的终点 | 环境改变的起点 |
| 角色 | 独白者 | 互动者 |

#### 3.3 协作的"语法"：多 Agent 系统的编排

从单体 Agent 转向多 Agent 网络，软件架构的隐喻从"机械装置"跃迁为"社会组织"。

**认知负荷的分流**：2023 年 GPT-4 发布当天，AutoGPT 诞生——智能并非单个模型的固有属性，而是"互动"的产物。

**A2A + MCP：双轨制协议**：MCP 解决 Agent 与工具的连接，A2A 解决 Agent 与 Agent 之间的连接，共同构成多 Agent 系统的双轨制协议。

> **通俗理解：MCP 是 AI 的"USB-C 接口"——让 Agent 能像插拔设备一样灵活挂载外部工具；A2A 则是 Agent 之间的"对讲机协议"，让多个 Agent 可以相互协作。**

**编排器（Orchestrator）**：当 Agent 数量增加，系统需要"大脑"来维持秩序——这就是 Orchestration 的核心使命。

#### 3.4 新的契约：人机协作的设计原则

人类与 AI 的关系不再局限于调用 API，而是转向设计协作模式。人类从代码的"建筑师"转变为 Agent 系统的"设计师与协作者"。

> **从 GoF 的 23 个设计模式到 Agent 的无限可能，我们跨越了软件工程的一个世纪：设计模式并未消亡，而是在进化；软件工程未曾终结，而是在重生；人类的角色没有消失，而是在升华。**


## 下篇：六大类 21 个核心设计模式

### 感知模式——系统与世界的接口层

传统软件是被动的，Agent 则是主动的。**感知的本质不是"看到所有"，而是"看到关键"并"主动寻找未知"。**

#### 注意力聚焦：信息"太多了"

工程本质是构建**认知漏斗**，用最低 Token 成本换取最高上下文质量——解决两个经济学问题：**凭什么删（价值评估）** 和 **删多少（预算约束）**。

三条工程路线：中间件模式(Lingua) / 存储优化模式(Prompt Caching) / 原生架构模式(MLA)

> **不要以"它能记住多少"为荣，而要以"它能精简多少"为傲。**

#### 多模态融合：信息"太杂了"

打破模态孤岛，建立**统一语义场**——图像像素向量与文本 Token 向量可以互相转化、互相解释。从"拼接式"向"原生式"演进。

> 多模态融合的最终目标，是让 AI 建立起一种**在场感(Presence)**——不再只是聊天机器人，而是一个存在于物理世界中的实体。

#### 主动感知：信息"太少了"

将 Agent 从**"被动的答题者"转变为"主动的调查员"**——当发现信息不足以支撑可信结论时，暂停生成答案，转而执行操作获取新证据。

| 子模式 | 解决的问题 | 核心机制 |
|--------|-----------|---------|
| 注意力聚焦 | 信息太多 | 认知漏斗，价值评估+预算约束 |
| 多模态融合 | 信息太杂 | 统一语义场，原生融合 |
| 主动感知 | 信息太少 | 元认知控制，信息觅食环 |

> **从"全知"到"求知"：真正的智能，不是因为你知道所有答案，而是当你不知道时，懂得如何去寻找。**

### 记忆模式——平台与协议的一等组件

**感知给出现在，推理创造洞见，记忆实现持续。**

#### 分层记忆模式：虚拟内存机制

Agent ≈ 操作系统内核：

| 层级 | 技术实现 | 类比 | 特点 |
|------|---------|------|------|
| L1 工作记忆 | Context Window | 大脑前额叶 / RAM | 容量有限，速度快，内容易失 |
| L2 短期缓存 | 摘要 + 情感缓冲区 | 信息中转站 | 防止过早丢失，也防止过早写入 L3 |
| L3 长期存储 | Vector DB + 知识图谱 | 海马体 / 图书馆 | 容量近乎无限，有检索延迟 |

两种流转：**溢出与巩固**（热→冷，L1 溢出信息经摘要进入 L2/L3） + **检索与唤醒**（冷→热，从 L3 召回相关历史注入 L1）

#### RAG 模式：检索与生成的交响

核心意图：通过动态检索外部知识库解决模型知识老化、长尾知识缺失和幻觉问题——**无需重新训练模型**。

四步核心机制：**索引**（把世界切片）→ **检索**（大海捞针）→ **重排序**（选择最佳）→ **生成**（基于资料回答）

> **RAG 最深刻的洞见：将"推理能力"（CPU）与"知识存储"（磁盘）解耦。** 以极低成本保持系统时效性，无需每次重新训练昂贵的 LLM。

#### 记忆模式小结

| 模式 | Agent 角色 | 作用 |
|------|-----------|------|
| 分层记忆 | 操作系统 | 统筹管理短期与长期信息的流动 |
| RAG | 图书馆 | 接入外部世界的静态知识 |
| 情节记忆 | 日记本 | 沉淀 Agent 自身交互产生的动态经验 |

> **从上下文工程到 MaaS 的跃迁，标志着记忆正从"策略层面的技巧"升级为"智能时代的核心基础设施"。**

### 推理模式——理性地编织

记忆解决"知道什么"，推理解决"如何运用"。

#### System 1 与 System 2

| 系统 | 特点 | 适用场景 |
|------|------|---------|
| System 1 | 快速、直觉、依赖启发式 | 熟悉领域、低风险情境 |
| System 2 | 缓慢、刻意、依赖反思式 | 复杂判断、强约束任务 |

#### 三种基本推理范式 + 三层抽象

三种基本范式：**演绎**（从一般规则推导具体结论）/**归纳**（从实例抽象一般规律）/**类比**（以已知推未知）

工程化抽象：**结构层**（思维容器）→ **流程层**（多路径推演）→ **反思层**（元推理）

#### 四种典型推理模式

| 模式 | 问题特征 | 核心机制 | 隐喻 |
|------|---------|---------|------|
| 思维链(CoT) | 问题清晰、路径明确 | 线性逐步推进 | 走钢丝 |
| 思维树(ToT) | 多分支、需权衡 | 启发式搜索、剪枝回溯 | 迷宫探路 |
| 思维图(GoT) | 复杂依赖、循环非线性 | 图结构编织、多轮迭代 | 织布机 |
| 类比推理 | 新颖问题、数据稀缺 | 结构映射、少样本学习 | 举一反三 |

#### 推理模式小结：交响乐隐喻

| 模式 | 乐器 | 擅长场景 |
|------|------|---------|
| 思维链 | 小提琴 | 数学与逻辑推导 |
| 思维树 | 钢琴 | 全局规划、试错回溯 |
| 思维图 | 电子合成器 | 多源信息整合 |
| 类比推理 | 鼓点 | 跨领域灵感激发 |

> **一位优秀的 Agent 架构师不应迷信单一推理模式，而应善于指挥整支认知"乐团"。** 面对陌生难题，先敲类比推理的鼓点；方向初现后，启思维树的钢琴；路径选定，交由思维链的小提琴严谨演绎；最后调用思维图的合成器打磨升华。

### 行动模式——决策的进阶之路

如果说推理模式是 Agent 的"参谋部"，行动模式便是 Agent 的"远征军"——走出大脑，迈向现实世界。

| 能力 | 模式 | 解决的问题 |
|------|------|-----------|
| 边想边打 | ReAct | 在行动中实时获取信息，动态调整策略 |
| 运筹帷幄 | 规划—执行 | 制订全局战略，分解为可执行步骤 |
| 调兵遣将 | 工具编排 | 精准选择、协同调配海量外部工具 |
| 自我进化 | 自适应策略 | 从成败中总结经验，动态优化策略 |

**ReAct**：看图规划 → 采取行动 → 观察反馈——**推理轨迹追踪中间决策，行动赋予探索环境获取外部信息的能力**。

**自适应策略 vs 神创论**：前三种模式属于"神创论"——工程师预先设定了 Agent 的行为逻辑；自适应策略是"进化论"——通过**试错、反馈和选择**逐渐演化出最优决策策略，从根本上克服系统僵化性。

> **当 Agent 能够感知、记忆、推理，并以明智且适应性的方式行动时，它已近乎一个完整的智能系统。** 但它仍存在致命弱点：可能对自己的错误深信不疑，陷入自我强化的逻辑闭环。

### 反思模式——AI 的灵魂工程学

感知使其看见世界，记忆使其连接时间，推理使其构建逻辑，行动使其付诸实施，而反思则使其判断这一切是否正确。

#### 三种反思模式

| 模式 | 关注点 | 作用对象 | 类比 | 时间尺度 |
|------|--------|---------|------|---------|
| 自我修正 | 当下(Now) | 输出结果 | 橡皮擦 | 毫秒级 |
| 反思记忆 | 下次(Next Time) | 情景记忆 | 错题本 | 分钟级 |
| 元学习 | 长远(Long-term) | System Prompt/策略 | 修订教科书 | 日/周级 |

**自我修正**：借助模型自身批判能力或外部工具验证，在交付用户前自动识别并纠正幻觉、逻辑错误——写错就擦，但仅限于当前任务。

**反思记忆**：任务失败时不停留于重试，生成"语言形式的教训"存入长期记忆。**Agent 不需要微调，只需更新"经验条目"即可实现持续进化。**

**元学习**：收集大量执行轨迹，借助优化器自动迭代 Prompt 和执行参数——这是"反思的反思"，从关注"任务是否正确"上升到审视"方法是否恰当"。

#### 感知/记忆/推理/决策/反思 = 眼睛/神经/大脑/肌肉/灵魂

| 能力 | 类比 | 赋予系统 |
|------|------|---------|
| 感知 | 眼睛 | 捕捉世界的信息 |
| 记忆 | 神经 | 承载经验的痕迹 |
| 推理 | 大脑 | 编织逻辑的网络 |
| 决策 | 肌肉 | 驱动行动的执行 |
| 反思 | 灵魂 | 对自身局限的觉察、对错误的不安、对更好答案的渴望 |

> **机器何时拥有灵魂？当它开始为自己的错误感到不安时。**

### 协作模式——协作的终局

单体 Agent 形成了完整的"心智闭环"，但真正的智慧不止步于自我完善，更在于与他人共同建构意义。

**智能并非孤独的函数，而是关系的网络。** AI 正从"工具时代"迈入"社会时代"。

| 协作方式 | 类比 | 说明 |
|---------|------|------|
| 辩论（对抗） | 法庭正反双方辩论 | 真理在交锋中清晰，多角度对抗性推演 |
| 委托（层级） | 经理指挥工人 | 目标层层分解，高效执行 |
| 路由（分发） | 医院分诊台 | 将任务精准分配到最适合的 Agent |
| 群体（涌现） | 蚁群迁徙 | 无需明确指挥者，自组织展现惊人效率 |

> **智能的最高形态，不在于独立思考，而在于共同进化。**


## 后记：从软件工程到 Agent 工程的生物化演进

### 牛顿力学的黄昏，达尔文逻辑的黎明

传统软件工程建立在牛顿力学隐喻之上：世界如精密钟表，齿轮严丝合缝——输入 A，必然输出 B。追求零熵，将一切不确定性视为 bug。

> **我们正从确定性工程转向概率性工程：不再追求如建造大教堂般严丝合缝的控制，而是致力于培育如热带雨林般生生不息、具备反脆弱性的系统。**

### 软件的生物化

| 设计模式 | 生物学对应 | 生命特征 |
|---------|-----------|---------|
| 感知模式 | 视觉与听觉的进化 | 主动"觅食"式感知 |
| 记忆模式 | 海马体与大脑皮质协作 | 短期到长期的记忆固化 |
| ReAct | 神经反射弧 | 感知-行动快速闭环 |
| 群体模式 | 蚁群与椋鸟群 | 局部交互涌现集体智慧 |

软件不再是僵化的代码块，展现出：**生长性**（通过 RAG 和情节记忆不断积累）/**适应性**（借助自适应策略动态调整）/**繁殖性**（利用元学习生成新 Prompt）

> 我们正见证硅基生命的"寒武纪大爆发"。

### 架构师的新角色：熵的园丁

新范式下，架构师从精准控制每一块砖位置的"建筑师"，转变为管理整个生态系统的"园丁"：

- **无法命令植物"必须长到 1m 高"，但可以浇水施肥**——优化数据质量，提供知识滋养系统
- **无法彻底阻止杂草生长（如幻觉），但可以修剪枝叶**——设置护栏，引入批判机制
- **无法预设每一朵花何时开放（如涌现），但可以营造适宜的环境**——设计 A2A 协议，搭建 Swarm 平台

> **园丁的智慧，在于懂得"适度失控"。唯有在混沌的边缘，智能才会真正涌现。**
